# MusubiReader 設計ドキュメント

- **作成日**: 2026-11-21
- **対象プロジェクト**: MusubiReader（iOS向けモダンRSS & まとめキュレーションリーダー）
- **ステータス**: 承認済み（実装計画フェーズへ移行）

---

## 1. 意図と背景（Intent & Why）

既存の普段使いしている5ch/2chまとめ系RSSリーダーには「インストールしてすぐ5ch/2chまとめが広告なしでサクッと読める」という非常に優れた初期体験がある一方、以下の強い不満がある。

1. **UIが15年前で止まっている**
2. **UXが非直感的で、知らないアイコンを触るのが怖い（「壊しそう」という不安感）**
3. **非同期アップデートやアルゴリズムによるキュレーションがない**（毎回手動でトップ画面を更新し、絞り込みはカテゴリ切替かその場の手動検索のみ。バックグラウンドでの検索監視やヒット時通知がない）
4. **先読みキャッシュがない**（Wi-Fi環境で記事を富豪的に先読みしておき、未読を自動パージする仕組みがない）

一方で、汎用的なRSSリーダーへ広げようとすると「汎用 vs 特化」の二項対立に陥りがちだが、本プロジェクトではこれを**「扱うサイトの種類」ではなく「ユーザーの関わり方（流し読み vs 待ち受け）」の軸**で再定義する。

- **流し読み（すぐ楽しい入口）**: インストール直後から5ch/2chまとめパックが有効になっており、ゼロ設定でカテゴリ別に広告なしでサクッと読める体験を絶対に壊さない。
- **待ち受け（興味を仕込んで育てる体験）**: `tech` 系などの興味キーワードを登録しておくと、裏側で自動監視してマッチした記事をキュレーション＆通知する。ここに汎用RSS（技術ブログ、ニュースサイト等）を追加していくことで、5chまとめも汎用RSSも横断して「自分の興味の網」に引っかかる体験へ自然に育つ。

企業製の既存アプリに対して、ホビープログラマのフットワークとモダンなUX設計で「個人開発でもここまで行ける」を示すことを目指す。まずは開発者自身の手元の **iPhone 16 でドッグフーディング**し、その後 **App Store 公開**を行う。

## 2. ゴール / ノンゴール / アンチゴール

### ゴール（Goals）
- **ゼロ設定の即時体験**: 初回起動直後から5ch/2chまとめがカテゴリ別・広告なしで閲覧できること。
- **怖くないモダンUI/UX**: 15年前の多機能ごちゃごちゃUIを脱却し、初見でも迷わず・壊す不安なく触れるシンプルな操作体系にすること。
- **興味ワードによる自動キュレーション＆通知**: 登録したキーワード（例: tech関連ワード）にマッチする記事をバックグラウンドで自動抽出し、専用ビューへのキュレーションとローカル通知を行うこと。
- **Wi-Fi時の優先プリフェッチ＆自動パージ**: Wi-Fi接続時にフィード全件を取得し、よく読むカテゴリや登録ワードにヒットした記事を優先的に先読みキャッシュする。読まれなかった記事は一定期間などのアルゴリズムで自動パージしてストレージを圧迫しないこと。
- **汎用RSSへの自然な拡張**: 5chまとめパックに加えて、任意のRSS/Atomフィードを追加でき、同じキュレーション・広告ブロック・先読み基盤の上で快適に読めること。
- **ホビー開発で継続運用できる軽さ**: サーバー維持費・常時運用コストをほぼゼロに抑えつつ、サイトURL変更・広告ルール・UI/ロジック改善を素早く配信できること。

### ノンゴール（Non-Goals / 初期スコープ外）
- **常時クロール用バックエンドサーバーの構築・運用**: 数分以内のリアルタイムAPNsプッシュ通知や、ユーザー間ランキング等のサーバー集計機能は初期スコープ外とする。
- **Web版の同時リリース**: 将来のWeb展開を見据えてTypeScript層を分離しやすい構造にするが、初期リリースはiOS（iPhone）に集中する。
- **全記事ページの完全オフライン保存**: 初期フェーズでは全フィードの全HTML/画像を無差別に丸ごとオフライン保存するのではなく、優先プリフェッチ（フィード全件＋よく読むカテゴリ＆ワードヒット記事）に絞る。
- **アカウント登録・クラウド同期**: 初期フェーズではオンデバイス完結とし、ログインやマルチデバイス同期は持たない。

### アンチゴール（Anti-Goals / こうなったら失敗）
- **設定・アイコン地獄の再発**: 汎用RSS機能や高度な設定を前面に出しすぎて、「何のボタンかわからず押すのが怖い」UXになってしまうこと。
- **空っぽの初回起動**: 汎用RSSリーダーっぽさを優先するあまり、インストール直後にフィード登録を強要し「すぐまとめが見られる気持ちよさ」を失うこと。
- **広告がすり抜けて読みにくい／表示が壊れる**: WebViewの広告ブロックが弱くてまとめサイトが読みにくくなったり、逆に過度なHTML加工でまとめ特有の装飾（色文字・AA・埋め込み等）が崩れて楽しさが損なわれること。
- **ホビー開発が詰む運用負荷**: サーバー費用や保守作業、App Store審査待ちに追われて開発・改善が止まってしまうこと。

## 3. 制約条件（Constraints）

- **ターゲット環境**: まずは開発者の手元の **iPhone 16（実機ドッグフーディング）**、その後 **App Store 公開**。
- **iOSバックグラウンド実行の制約**:
  - `BGAppRefreshTask` / `BGProcessingTask` はOSがバッテリー・充電状態・Wi-Fi・利用頻度に応じてスケジューリングするため、バックグラウンド巡回・ローカル通知はリアルタイム（数分以内）ではなく「数十分〜数時間おき／充電＋Wi-Fi時のスキマ」での実行となる。
- **App Store 審査への配慮**:
  - 広告ブロックはApple公式の `WKContentRuleList` を使用する。
  - 5ch/2chまとめサイトには不適切なコンテンツ（NSFW・過激表現等）が混入するリスクがあるため、初期プリセットパックは健全寄りの厳選リストとし、ユーザーによるサイト単位のミュート／非表示およびNGワードフィルタを備える。
  - OTA更新（`EAS Update`）はAppleガイドラインに準拠し、UI改善・バグ修正・キュレーションロジック調整の範囲で運用する。
- **個人開発コスト制約**: 常時稼働サーバーを持たず、外部ホストは無料枠で運用できる静的ファイル（GitHub Pages / Cloudflare R2等）に留める。

## 4. 検討したアプローチと選定理由（Approaches）

### 4-1. システム構成（データ取得・配布アーキテクチャ）

| アプローチ | 概要 | トレードオフ |
| :--- | :--- | :--- |
| **案A: 完全オンデバイス完結** | RSS取得・キュレーション・プリフェッチ・通知をすべて端末内で完結。初期まとめリスト・広告ルールもアプリ同梱。 | 維持費0円・最速で着手できるが、まとめサイトの閉鎖/URL変更や新広告ドメイン対応のたびにApp Store審査が必要になる。 |
| **案B: オンデバイス主体 ＋ 静的JSON外出し（採用）** | 基本処理はすべて端末内完結（サーバーレス）。**プリセットパック定義JSON**と**広告ブロックルールJSON**の2つだけを静的ファイルとして外部ホストし、アプリが定期取得する。 | 維持費ほぼ0円・プライバシー安全を保ちつつ、最も腐りやすい「まとめサイト一覧」と「広告ルール」をApp Store審査なしで即更新できる。通知の即時性だけはiOSバックグラウンド制御に委ねる。 |
| **案C: 軽量バックエンド併用** | Cloudflare Workers等のサーバーレス基盤でフィードを常時クロールし、登録ワードヒット時にAPNsで即座にプッシュ通知する。 | リアルタイム通知や集計系機能に強いが、サーバー・DB・プッシュ証明書・ユーザー設定管理の実装・運用負荷が一気に跳ね上がり、ホビー開発の初速と継続性を損なう。 |

**選定**: **案B** を採用。まず案BでApp Store公開まで走り切り、将来リアルタイム通知がどうしても必要になった場合に案Cへ拡張可能な余地を残す。

### 4-2. アプリ技術スタック

| アプローチ | 概要 | トレードオフ |
| :--- | :--- | :--- |
| **スタック1: Expo (React Native + TypeScript) ＋ 薄いSwiftモジュール（採用）** | アプリ本体はExpo（Development Build / CNG）＋TypeScriptで構築。広告ブロックWebViewの心臓部のみExpo Modules APIで薄いSwiftネイティブモジュール（`WKWebView` + `WKContentRuleList`）を実装する。 | `EAS Update` によるOn-the-flyなOTA更新が可能で、将来的なWeb展開（React Native Web / Expo Router）へロジック・UIを流用しやすい。Expo GoではなくDevelopment Build（Mac + Xcode）が必要になるが、実機ドッグフーディング環境があるため問題ない。 |
| **スタック2: Swift + SwiftUI 完全ネイティブ** | iOS標準フレームワークのみで完結させる構成。 | iOS単体としてのビルド・OS連携は最もシンプルだが、UI/ロジックのOTA更新ができず、将来のWeb展開時は別実装となる。 |

**選定**: **スタック1** を採用。案Bの「静的JSON外出し」と `EAS Update` の「OTA更新」を組み合わせることで、企業アプリを上回る改善スピードを実現する。

## 5. 合意済みの機能・体験仕様（What the User Decided）

### 5-1. 二軸の体験モデル（流し読み × 待ち受け）
- **流し読み（パック単位 × カテゴリ閲覧）**:
  - 初期状態で「5ch/2chまとめパック」が組み込まれており、インストール直後からカテゴリ切り替えで閲覧できる。
  - ホーム画面では **パック単位（例:「5chまとめ」「Tech」「マイRSS」）で切り替えて閲覧** する構造とし、汎用RSSや他パックを追加しても「いつもの5chまとめ閲覧」の純度を壊さない。
  - 広告ブロック付きWebViewで、まとめサイト特有の装飾を壊さずに快適に読める。
- **待ち受け（全パック横断の興味ワード・キュレーション）**:
  - ユーザーが興味のあるキーワード（例: `tech` 系ワード）を登録できる。
  - v1のキュレーションは **「登録した興味ワードの一致 ＋ 鮮度順」** でスタートする（閲覧履歴に基づく暗黙的レコメンドはドッグフーディング後の将来拡張）。
  - バックグラウンドおよびアプリ起動時の非同期更新で、**全パック・独自追加の汎用RSSを横断して**新着記事のRSS/Atomメタデータ（タイトル・要約・カテゴリタグ）と照合し、マッチした記事をピックアップ枠に集約＋ローカル通知する。
- **汎用RSSの拡張**:
  - 任意のRSS/Atom URLを追加でき、マイRSSパック（または指定パック）に組み込める。追加した汎用RSSも興味ワード監視・キュレーション・プリフェッチ・広告ブロックの対象となる。

### 5-2. Wi-Fi時の優先プリフェッチ＆自動パージ（当座の方針）
- **Wi-Fi接続時の非同期更新**:
  - 登録されている全フィードのRSS/Atomを非同期取得し、記事一覧・メタデータ・検索用テキストをローカルDBへ保存する。
  - **優先プリフェッチ対象**: 「よく読むカテゴリ」および「登録した興味ワードにヒットした記事」について、記事ページのHTMLおよび主要画像リソースを優先的に先読みダウンロードする。
  - **オフライン閲覧の到達点（v1）**: オンライン時の表示爆速化を主眼とし、完全オフライン環境では一部装飾の省略を許容して「本文と主要画像が読めればOK」という簡易オフライン表示に割り切る（完全オフラインでのCSS完全再現のためのローカルHTTPプロキシ等はv1では作らず、早期ドッグフーディングを優先する）。
- **自動パージ**:
  - 読まれなかった記事およびその先読みキャッシュは、経過期間などのアルゴリズムによって自動的にパージ（削除）し、ストレージを健全に保つ。

### 5-3. 静的JSON外出し（案B）
- アプリ同梱のフォールバック（初期内蔵JSON）を持ちつつ、外部ホストされた以下の静的JSONを定期取得・キャッシュ更新する。
  1. **プリセットパックJSON**: 5ch/2chまとめパック、Techパック等のフィード定義（サイト名、RSS URL、カテゴリ、有効フラグ等）
  2. **広告ブロックルールJSON**: `WKContentRuleList` 互換のJSONルールセット

## 6. エージェントによる仮決め（My Calls — 承認時に確認対象）

ユーザーから明示指定がなかった以下の細部は、初版（ドッグフーディング版）の合理的なデフォルトとして以下のように仮決めする。

- **画面の基本構造（3タブ構成案）**:
  1. **ホーム（流し読み）**: 最上部にパック切替、その下にカテゴリタブ、本文エリアに記事リスト。謎アイコンを置かず「タップで読む」「長押し/スワイプで最小限の操作（後で読む・サイト非表示）」に絞る。
  2. **ピックアップ（待ち受けキュレーション＆保存済み）**: 上部セグメントで「キーワード一致 / 保存済み（後で読む）」を切り替えられる構成とし、3タブのシンプルさを維持する。ここから興味ワードの追加・編集ができる。
  3. **ソース / 設定**: プリセットパックのON/OFF、汎用RSS URLの追加、NGワード/ミュート管理、Wi-Fiプリフェッチ・キャッシュ管理。
- **照合対象（キーワード＆NGワード）**: 優先プリフェッチ方針と整合させるため、v1の興味ワード照合およびNGワードフィルタはRSS/Atomのメタデータ（タイトル・要約・カテゴリタグ）を対象とする。
- **静的JSON更新時のローカル設定マージ仕様**: 外部のプリセットパックJSONには不変の `packId` / `siteId`、スキーマバージョン、廃止フラグ（`deprecated`）を持たせる。ローカルDBでは「リモート定義カタログ」と「ユーザー設定（パックON/OFF、個別サイトミュート、独自追加RSS）」を別テーブルで分離管理し、カタログ更新時にURL変更や新サイト追加を反映しつつ、ユーザーのミュート設定や独自RSSが絶対に消えないようにする。
- **「よく読むカテゴリ」の判定方法**: 直近14日間のカテゴリ別記事閲覧数上位（例: 上位2〜3カテゴリ）を自動判定し、優先プリフェッチ対象とする。
- **自動パージと保存済み記事の保護ルール**: 未読記事のプリフェッチキャッシュは取得から **3日（72時間）** で自動削除、記事メタデータ自体は **14日** で自動削除する。ストレージ上限（例: 200MB）を超えた場合は古い未読キャッシュからLRU削除する。保存済み（後で読む）記事はメタデータ削除対象外とし、キャッシュも別枠（上限例: 50MB）で優先保持する。
- **v1のカテゴリ管理**: パック内カテゴリはカタログ定義をベースとし、独自追加した汎用RSSは「マイRSS」パック配下でシンプルに管理する（複雑なユーザー定義カテゴリ階層・並び替えUIは初期スコープ外）。
- **静的JSONのホスト先**: GitHub Pages（または同リポジトリの特定ブランチ/Cloudflare R2）を採用し、通信失敗時はアプリ同梱のフォールバックJSONを使用する。
- **ローカルDB**: `expo-sqlite` を使用し、フィード・記事・興味ワード・閲覧履歴・キャッシュ管理テーブルをオンデバイスで管理する。

## 7. ビルダーに委ねる事項（What's Left to the Builder）

以下は実装計画（Plan）および実装フェーズでビルダーが最適な技術判断を行ってよい領域とする。

- Expo SDKバージョン、ディレクトリ構成（Expo Router構成、ドメインロジックとUIの分離方法）、状態管理ライブラリ（Zustand / TanStack Query 等）の選定。
- SQLiteの具体的なテーブル定義・マイグレーション管理・全文検索（FTS5利用等）の実装詳細。
- RSS 1.0 / 2.0 / Atom パーサーの選定および文字コード・不正XMLへの耐性実装。
- Expo Modules API を用いたSwiftネイティブモジュール（`WKWebView` + `WKContentRuleList` + ローカルプリフェッチキャッシュ連携）の内部実装詳細。
- キュレーションスコアの具体的な重み付け式（キーワード一致箇所の重み、鮮度減衰など）と、ユニットテスト設計。
- 広告ブロック初期ルールセットの具体的なドメインリスト・CSS隠蔽ルール、および初期プリセットパックに含める具体的な健全寄り5chまとめサイト・Techサイトの候補リスト選定（公開前にユーザー確認）。
- `BGAppRefreshTask` / `BGProcessingTask` の登録・再スケジュール制御およびWi-Fi判定の実装詳細。
